# `pkg/backbone/store` walkthrough

This explains the `store` package - the local metadata/file layout behind
`PullRootFS`/`ListRootFS`/`RootFSStatus`/`RemoveRootFS` - and the reasoning behind
its specific design choices.

## What it's for

`PullRootFS` (see `1.md`) needs somewhere durable to keep the ext4 images it
packs, plus enough metadata to answer "have I already pulled this?",
"what's pulled right now?", and "where exactly is the file for this digest?"
without re-contacting a registry. `store.Store` is that - a small,
single-host, content-addressed cache. It is **not** a database; it's a
directory with a predictable layout:

```
<root>/images/sha256-<hex>.ext4   the packed image
<root>/images/sha256-<hex>.json   its metadata sidecar
<root>/tmp/<random>/              scratch space for in-progress pulls
```

## The API

```go
type Entry struct {
	Digest          string
	RepoTags        []string
	RepoDigests     []string
	Size            uint64
	SpecImage       string
	SpecAnnotations map[string]string
	CreatedAt       time.Time
}

func Open(root string) (*Store, error)
func (s *Store) Lookup(digest string) (Entry, bool, error)
func (s *Store) LookupByRef(ref string) (Entry, bool, error)
func (s *Store) Resolve(ref string) (Entry, bool, error)
func (s *Store) ImagePath(digest string) (string, error)
func (s *Store) Stage() (extractDir, tmpImagePath string, cleanup func(), err error)
func (s *Store) Commit(entry Entry, tmpImagePath string) error
func (s *Store) AddRef(digest, repoTag, repoDigest string) error
func (s *Store) Remove(digest string) error
func (s *Store) List() ([]Entry, error)
```

`Stage`/`Commit` are the write path (used once, by `PullRootFS`, on a cache
miss). `Lookup`/`LookupByRef`/`Resolve`/`List` are the read path, used by all
four RPCs. `AddRef` is the cheap write used on a cache *hit* - recording a new
tag against already-pulled content without touching its image file.

## Design decisions, and why

### Content-addressed by digest, not by tag

The directory and file names are built from the image's manifest digest
(`sha256:<hex>` → `sha256-<hex>.ext4`), never from a tag. Tags are mutable and
ambiguous - `alpine:latest` means different bytes at different times, or on
different registries. A digest is the content. This is the same principle
every real container runtime's local image store uses (Docker's image store,
containerd's content store, the OCI Image Layout spec): key by digest, treat
tags as *pointers into* that keyspace rather than keys themselves. That's
exactly what `RepoTags`/`RepoDigests` are here - a list of names known to
resolve to one digest-keyed entry, not separate entries of their own.

### A JSON sidecar per entry, not one shared index file

This was a deliberate choice between two options, made explicit at design
time:

- **One sidecar per entry** (what's implemented): `Commit`/`AddRef` only ever
  touch one entry's own files. A write is "create a temp file, `os.Rename` it
  into place" - the same atomicity trick as the image file itself. A corrupt or
  truncated sidecar only loses metadata for *that one* image. `List()` costs a
  directory scan plus N small JSON parses.
- **One shared index file** (the alternative): would need the *entire* index
  rewritten and locked on every single pull or removal, serializing unrelated
  pulls against each other. A crash mid-rewrite could lose every entry's
  metadata at once instead of one.

At the scale this store actually operates at - one host's local rootfs cache,
realistically dozens to a few hundred entries - the shared-index approach's only
real advantage (fast aggregate listing without a directory scan) doesn't matter,
and its downsides (contention, blast radius) do. Hence: a sidecar per entry.

### The sidecar is hand-written fields, not the proto message

`Entry.SpecImage`/`SpecAnnotations` are plain fields, not an embedded
`*v1.RootFSSpec`. Protobuf messages don't round-trip cleanly through
`encoding/json` in general (`oneof`s, certain map encodings), and even where
they happen to work today, that's an accident of the current `.proto`, not a
guarantee. Flattening the two fields we actually need decouples the on-disk
format from however the proto evolves later - a wire-format change to
`RootFSSpec` shouldn't require a migration of every sidecar already on disk.

### Stage, then atomically rename - never write in place

```go
extractDir, tmpImage, cleanup, err := s.Stage()   // scratch space under tmp/
defer cleanup()
... unpack and pack into extractDir / tmpImage ...
s.Commit(entry, tmpImage)                         // os.Rename into images/
```

Every expensive step happens in `<root>/tmp/<random>/`, which is invisible to
every read path (`Lookup`, `List`, …). The *only* thing that makes an entry
exist, as far as a reader is concerned, is the `os.Rename` inside `Commit`
(same trick again for the sidecar: write `<path>.tmp`, then rename over
`<path>`). `os.Rename` within the same filesystem is atomic on Linux, so there
is no window where a reader can observe a half-written image or a half-written
sidecar. If `PullRootFS` crashes or errors at any point before `Commit`, the
store is left exactly as it was before the call started - the deferred
`cleanup()` just deletes the now-irrelevant scratch directory. This is the
same pattern git uses for its object store and containerd uses for its content
store: build in a staging area, publish by rename.

### `Open` sweeps stale scratch directories

```go
func (s *Store) sweepStaleTmp() {
	... remove anything under tmp/ older than 1 hour ...
}
```

Because nothing under `tmp/` is ever load-bearing once a pull finishes (success
*or* failure - `cleanup()` handles both), anything still sitting there on the
*next* process start can only be debris from a pull that was killed mid-flight
(crash, OOM, `kill -9`). Sweeping it on `Open` is the same "GC orphaned
staging state on startup" pattern containerd's snapshotters and Docker's
graphdriver use, scaled down to fit a single JSON-sidecar store. The one-hour
cutoff is conservative headroom, not a correctness requirement, since nothing
currently running should have a multi-hour-old scratch dir in the first place.

### `Resolve` accepts either a bare digest or any known reference

```go
func (s *Store) Resolve(ref string) (Entry, bool, error) {
	if digestPattern.MatchString(ref) {
		if e, ok, err := s.Lookup(ref); err != nil || ok {
			return e, ok, err
		}
	}
	return s.LookupByRef(ref)
}
```

`RootFSSpec.image` is documented as accepting a tag, a digest, or (per the
proto comment) other forms - and `PullRootFSResponse.rootfs_ref` is always a
bare digest. So `RootFSStatus`/`RemoveRootFS` need to accept *either* shape
without the caller having to know which one they're holding. `Resolve` tries
the cheap, unambiguous path first (it already looks like `sha256:<hex>` → go
straight to that file), and only falls back to scanning tags/digests when it
doesn't.

### The digest regex doubles as a path-traversal guard

```go
var digestPattern = regexp.MustCompile(`^[a-z0-9]+(?:[._+-][a-z0-9]+)*:[0-9A-Fa-f]+$`)

func digestFileBase(digest string) (string, error) {
	if !digestPattern.MatchString(digest) {
		return "", fmt.Errorf("store: invalid digest %q", digest)
	}
	return strings.Replace(digest, ":", "-", 1), nil
}
```

Every file path the store touches is built from `digestFileBase`, and every
public method that takes a digest runs it through this check first. A digest
is never attacker-controlled free text by the time it gets here (it comes from
`img.Digest()`, computed by `go-containerregistry` from the actual manifest
bytes) - but validating it anyway means a string like `"../../etc/passwd"`
can never reach `filepath.Join` and turn into a path outside `<root>/images/`,
regardless of how it got there.

### A mutex, for correctness under concurrency - not performance

```go
type Store struct {
	root string
	mu   sync.Mutex
}
```

`Commit` and `AddRef` both read-then-write a sidecar (read the existing entry,
merge `RepoTags`/`RepoDigests` into it, write it back). Two goroutines doing
that concurrently for the *same* digest is a real scenario - e.g. two
`PullRootFS` calls racing to pull the same not-yet-cached image - and without
the lock, a classic read-modify-write race could drop one goroutine's merged
tag. The image file itself doesn't need locking (its content is
content-addressed and immutable - whoever wins the `os.Rename` race writes
byte-identical content), so the mutex only ever guards the sidecar
read-modify-write.

## Where this came from

The overall shape - digest-addressed storage, tags as aliases rather than
keys, stage-then-rename for atomicity, startup GC of orphaned scratch state -
isn't novel; it's the same small set of ideas every real container image
store (Docker, containerd, the OCI Image Layout spec, even git's object
store) converges on, because they're all solving the same underlying problem:
make "is this content already here?" and "publish this content" both cheap
and crash-safe. What's specific to this implementation is scoping it down to
match what's actually needed here - a single host's local cache of a few
hundred entries at most - which is why it's a directory of JSON sidecars
instead of a database or a single index file: the simpler option is also the
more robust one at this scale.
